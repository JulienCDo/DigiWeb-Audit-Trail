# DigiWeb Audit Trail Event Catalog

## 1. Purpose

This document defines the audit events supported by the DigiWeb Audit Trail MVP.

Each event must:

- use the canonical event model defined in [`02-event-model.md`](./02-event-model.md);
- have a unique and stable event type;
- identify the tenant;
- identify the actor or system responsible for the action;
- identify the target entity when applicable;
- contain only the data required for traceability and reporting;
- be immutable after acceptance.

## 2. MVP event summary

| Event type | Category | Actor | Target | Outcome | Severity |
|---|---|---|---|---|---|
| `LOGIN` | Authentication | User | Optional | Success, Failure, Denied | Info, Warning |
| `LOGOUT` | Authentication | User, System | Optional | Success | Info |
| `DICTATION_ACCESSED` | Dictation | User | Dictation | Success, Denied | Info, Warning |
| `DICTATION_STATUS_CHANGED` | Dictation | User, Service, System | Dictation | Success, Failure | Info, Warning |
| `DICTATION_PURGED` | Dictation | User, Service, System | Dictation | Success, Failure | Warning, Critical |
| `TRANSCRIPTION_MODIFIED` | Transcription | User, Service | Transcription | Success, Failure | Info, Warning |
| `TRANSCRIPTION_STATUS_CHANGED` | Transcription | User, Service, System | Transcription | Success, Failure | Info, Warning |
| `WORK_SESSION` | Productivity | User, System | Dictation or Transcription | Success, Failure | Info, Warning |
| `REPORT_EXECUTED` | Reporting | User, Service | Report | Success, Failure | Info, Warning |

## 3. Event definitions

## 3.1 LOGIN

### Description

Records a login attempt made by a user.

The event must be recorded for successful, failed, and denied login attempts.

### Standard values

| Field | Value |
|---|---|
| `category` | `Authentication` |
| `target.type` | `USER`, when available |
| `outcome` | `SUCCESS`, `FAILURE`, or `DENIED` |
| `severity` | `INFO` for success, `WARNING` for failure or denial |

### Required fields

- `tenantId`
- `application`
- `actor.type`
- `actor.id`
- `actor.displayName`, when available
- `target.id`, when the user is identified
- `timestampUtc`
- `outcome`
- `severity`

### Event-specific data

```json
{
  "authenticationMethod": "PASSWORD",
  "failureReason": "INVALID_CREDENTIALS",
  "ipAddress": "10.10.10.10",
  "workstation": "WS-123"
}
```

### Rules

- Do not store passwords, tokens, or authentication secrets.
- `failureReason` is required when `outcome` is `FAILURE` or `DENIED`.
- User information must be minimized according to applicable privacy policies.
- IP address and workstation information must be recorded only when permitted.

### Reports

- Security Audit Report
- User Activity Audit Report

## 3.5 DICTATION_PURGED

### Description

Records the permanent purge of a dictation or an associated audio recording.

This event is required for retention, compliance, and investigation purposes.

### Standard values

| Field | Value |
|---|---|
| `category` | `Dictation` |
| `target.type` | `DICTATION` |
| `outcome` | `SUCCESS` or `FAILURE` |
| `severity` | `CRITICAL` for successful permanent purge, `WARNING` for failure |

### Required fields

- `tenantId`
- `application`
- `actor.type`
- `actor.id`
- `target.type`
- `target.id`
- `timestampUtc`
- `outcome`
- `severity`
- `data.purgeType`
- `data.reason`

### Event-specific data

```json
{
  "purgeType": "RETENTION_POLICY",
  "reason": "RETENTION_PERIOD_EXPIRED",
  "audioRecordingId": "AUD456",
  "purgedAtUtc": "2026-09-23T15:30:22.000Z"
}
```

Supported purge types:

```text
MANUAL
RETENTION_POLICY
SYSTEM
```

### Rules

- The event must not contain the audio content.
- The event must identify the affected dictation.
- The audio recording identifier should be included when applicable.
- A purge event must not be removed as part of normal application operations.

### Reports

- User Activity Audit Report
- Retention and Compliance Audit Report, when implemented

## 3.8 WORK_SESSION

### Description

Records a period of active work performed by a user or system on a dictation or transcription.

The event supports time analysis and productivity reporting.

A work session may be represented by:

- one event containing start and stop information; or
- separate start and stop events using the same `correlationId`.

The selected implementation must be consistent across all producing applications.

### Standard values

| Field | Value |
|---|---|
| `category` | `Productivity` |
| `target.type` | `DICTATION` or `TRANSCRIPTION` |
| `outcome` | `SUCCESS` or `FAILURE` |
| `severity` | `INFO` for success, `WARNING` for failure |

### Required fields

- `tenantId`
- `application`
- `actor.type`
- `actor.id`
- `target.type`
- `target.id`
- `timestampUtc`
- `outcome`
- `severity`
- `data.action`

### Event-specific data

```json
{
  "action": "STOP",
  "workType": "TRANSCRIPTION",
  "startedAtUtc": "2026-09-23T15:30:22.000Z",
  "stoppedAtUtc": "2026-09-23T15:48:22.000Z",
  "durationSeconds": 1080
}
```

Supported actions:

```text
START
STOP
```

Supported work types may include:

```text
TRANSCRIPTION
REVIEW
CORRECTION
```

### Rules

- `START` requires `startedAtUtc`.
- `STOP` requires `stoppedAtUtc` and `durationSeconds`.
- `durationSeconds` must be a non-negative integer.
- Start and stop events should use the same `correlationId`.
- The system must prevent negative or impossible durations.
- The event must not be used as a substitute for business completion events.

### Reports

- Time Analysis Report
- True Productivity Report
- User Activity Audit Report

## 5. Event production rules

### Successful operations

A successful business operation should produce an audit event only after the operation has been accepted by the originating business service.

### Failed operations

Failed operations must be audited when they are relevant to security, compliance, access investigation, or operational diagnosis.

### Denied operations

Access denials must be recorded when they represent a meaningful security or access event.

### System operations

System-generated events must identify the responsible service or process as the actor.

### Duplicate publication

Producers may retry event publication. The Audit Service must use the event `id` as the idempotency key and must not create duplicate records.

## 7. Catalog governance

A new event type may be added only when:

1. its business purpose is documented;
2. its actor and target are defined;
3. its required data is specified;
4. its privacy impact is assessed;
5. its associated reports are identified;
6. its contract version is defined;
7. the event is approved by the audit service owner.

Event names must not be reused for a different business meaning.

Existing event definitions must not be changed incompatibly without incrementing the event contract version.
